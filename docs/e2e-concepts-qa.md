# e2e 概念问答：从工作流到定位

> 整理自一次真实接入过程中的问答（2026-11）。背景：一个本地部署的考试系统（管理端、考生端、移动 Web 三端），用 e2e 从零建测试项目，模型走智谱 GLM，浏览器附着本地 Chrome。问题都是接入者真实问出的，按概念脉络重排；例子保留考试系统语境，结论对任何被测系统通用。

## 1. 典型工作流是"探索 → 生成用例 → 回归"吗？

基本正确，但有两处关键修正。

**修正一：探索不产出测试用例。** `npx e2e explore "<目标>"` 是侦察，不是生成器——agent 带着目标在应用里走一遍，输出一份发现报告，然后丢弃。测试文件不会从探索里自动冒出来，中间还有一步：**人来写测试**（实践中是 Claude Code 会话带着 e2e 技能，以探索报告和功能规格为输入，写出 `tests/*.e2e.ts`）。

**修正二："智能"只存在于首跑，之后全是回放。** 测试内部分两层：

- 确定性层：locator 断言（`expect(screen.getByRole(...))`、URL、元素存在）——从头到尾不碰模型
- 智能层：`agent.act("登录并开始考试")`——首跑时模型驱动，成功后动作序列录进 `.e2e/cache/`；之后每次回放的是录制，零模型调用

| 阶段 | 命令 | 模型调用 | 产物 |
|---|---|---|---|
| 建项目 | `npx e2e init` | 无 | 配置 |
| 探索（可选） | `npx e2e explore "..."` | 有 | 一次性发现报告 |
| 写测试 | 人 / Claude 写 `.e2e.ts` | — | 测试代码 |
| 首跑录制 | `npx e2e run --no-cache` | 有（仅 agent 步骤） | `.e2e/cache/` 录制 |
| 日常回归 | `npx e2e run` | 零 | 回放 + 断言 |
| UI 改版后 | 报 `REPLAY_STALE` → 重录 | 重录时有 | 新缓存，与改动同提交 |

## 2. 不做探索，它怎么知道我有哪些菜单、哪些功能？

"了解系统"和"跑 explore 命令"是两回事。写测试需要的知识有四个来源：

1. **人给的规格（决定"写哪些测试"）**。覆盖面从来不是 agent 逛出来的，是人定义的。路由表、账号场景矩阵——每个"账号 × 场景"格子就是一条待写测试。框架没有任何机制（也不应该有）替你判断"什么值得测"。
2. **MCP 实时观察（决定"怎么写"）**。写测试的会话通过 e2e MCP 服务器亲自打开系统看：`open_session` → 用真实账号登录 → 逐页 `observe`。`observe` 返回的语义树（角色、名称、状态）就是 locator 的直接来源——`getByRole('button', { name: '开始考试' })` 是从看到的真实结构里挑的，不是猜的。
3. **被测系统本身（可选）**。源码、自测套件、你的领域知识，随时可以流入。
4. **`e2e explore` 命令（补充）**。唯一价值是找"你不知道自己不知道"的东西——陌生用户视角乱走，撞见你以为不存在的死链、空状态、移动端崩坏。

所以跳过的只是 explore 这条**命令**，不是"探索"这个**活动**。观察永远会发生，只是形式变了：从"一次性、自主、输出报告你看"变成"写测试过程中、交互式、每看一页落成一行代码，你在旁边随时纠偏"。

## 3. 只提供了考生端路径，管理端没提供，要补吗？

菜单本身**不需要提供**——admin 登录走一遍，功能清单自动出来（结构层可以自动盘点）。但自动盘点直接落成的测试是**冒烟级**的：页面能开、表单能交、列表能显。三样东西永远不会自动出现：

| 知识 | 为什么必须人给 |
|---|---|
| 业务规则 | "发布后题目不可改"——agent 看得到界面，看不到规则；断言什么取决于预期是什么 |
| 优先级 | 盘点会列出全部菜单，但哪条链路最核心只有你定得了 |
| 数据操作边界 | 管理端测试是写操作，会真改开发库；哪些能造、怎么命名前缀、测完删不删，是约定 |

推荐混合流程：人给三样轻量物（核心链路、业务规则、数据边界）→ 会话自动盘点菜单 → 清单回来人划勾 → 再动笔。覆盖面仍然是人定的，只是从"手写清单"变成"机器起草、人审批"。

## 4. agent 把预期行为当 bug 了（"正式考试不能重复进入"案例），怎么处理？

这类问题叫**规格缺失型误报**。agent 的判断是有基线的，基线里没有你的业务规则时退回通用常识——而"考试开始后应能续答"是常识，"正式考试单次进入"是反常识的业务规则，必被误判。处理方法是让规则注入的层次往上升，一级比一级强：

- **第 1 级，agent 通用常识**：不给规则，agent 拿常识垫底 → 单次进入被当成"卡死的状态" → 结论"数据坏了，修数据"。
- **第 2 级，规则写进目标文本**：goal 和 explore 的目标文本会原文进入模型输入，规则可以随行：

  ```ts
  agent.act('以 stu_e2e2 进入 E2E切屏考试并作答。注意：切屏1次会被强制交卷，这是预期行为');
  ```

- **第 3 级，规则变成断言（最强）**：把反直觉规则直接写成预期结果——

  ```ts
  // 交卷后再试进入，被拦是预期
  expect(browser).toHaveURL(/\/my/);
  expect(screen.getByText(/不可重复进入|已交卷/)).toBeTruthy();
  ```

  规则一旦是断言，"对错"不再依赖任何模型的理解，测试定义本身说了什么是对的。

配套两条纪律：探索报告**是假设清单，不是结论**——发现"可疑行为"由懂业务的人裁决，人工 triage 是设计内的一环；agent 基于误诊提出的修复动作（改数据、删记录）没经确认一个都不执行。

还有一层容易被忽略：**单次进入 = 可消耗的测试资源**。测试每真跑一次烧一次进入次数，回放也会重放动作、同样烧。通行做法：流程类测试用"不限次"变体扛；规则本身用专门测试断言拦截态；并配"每轮可重置"的种子安排（重置脚本或每轮新建一次性数据）。

## 5. 这个项目到底是做什么的？

一句话：**它取代测试人员的"手"，不取代"脑"。**

| 知识 | 内容 | e2e 之后 |
|---|---|---|
| 测什么、对错标准（脑） | 覆盖哪些场景、业务规则、预期结果 | 仍然 100% 是人，且变成人的几乎全部工作 |
| 怎么操作浏览器（手） | 找按钮、填表、等加载、处理 iframe/动效 | agent 首跑自己会做，录下来之后回放 |

传统 Playwright 测试贵，贵在第二半：一个懂需求的测试人员把脑里的意图手工翻译成一串 `page.click()`、选择器、等待逻辑，UI 一改还得重翻译。e2e 干掉的是这层翻译；第一半没有被自动化，也不可能被自动化——**需求表达的质量直接就是测试的质量**，这个因果关系比以前更裸露。

测试人员的产出变了：从"一套 Playwright 脚本"变成"一份薄测试（一句话 goal + 一行断言）+ 覆盖面清单 + 业务规则清单"。代码打字可以交给 Claude，清单的内容、规则的准确性、优先级的判断都是人的。

## 6. 所以它是"用自然语言写测试脚本"？

接近了，但两个精度修正，恰好是这套方法好不好用的分水岭。

**修正一：自然语言只是测试的一半，另一半仍是代码。**

```ts
await agent.act('以 stu_e2e 登录，从我的考试列表进入 E2E模拟考试并开始作答');
// ↑ 自然语言：告诉 agent「做什么」。怎么找按钮、怎么过页面，它自己解决

expect(browser).toHaveURL(/\/exams\/\d+\/take/);
expect(screen.getByRole('button', { name: /交卷/ })).toBeTruthy();
// ↑ 代码：证明「做成了」。对错标准
```

纯自然语言的"成功"是模型自己说了算——它觉得做到了就算做到了，等于考生自己给自己判卷。断言是把判卷权拿回人手里。所以准确说法是**「操作用自然语言，对错用断言」**。

**修正二：自然语言只在首跑被理解一次。** 不是每次跑都让模型重新读那句话。首跑时模型把目标翻译成动作序列，录进缓存；之后每次回归回放的是录制，模型根本不参与。类比：自然语言是源码，录制是编译产物，回归是跑二进制——只有 UI 改版（`REPLAY_STALE`）才重新"编译"。这就是回归零模型成本、结果确定性的原因。

另外，自然语言是**按需选用**的，不是义务：目标导航用 `agent.act`；精确操作和验证用代码（例如切屏考试要用 `browser.evaluate` 触发 `visibilitychange`，这种精确控制交给自然语言反而不可靠）。

## 7. code agent 已经会写 Playwright 了，何必再用 e2e？

"测试人员用自然语言描述、code agent 直接生成 Playwright 脚本"这个流程确实成立，LLM 也确实熟 Playwright（参数权重里就有）。分歧不在"能不能"，在**产物形态和长期维护行为**。

**生成脚本是开环的，e2e 是闭环的。** Code agent 生成脚本时，把整个操作序列一次性写完——基于它之前看到的页面，冻结成选择器和点击流。首跑往往就错（选择器差一点、时序竞态、动态内容），然后进入"跑错 → 改代码 → 再跑"的迭代。脚本的正确性是**被相信的**。e2e 首跑时，agent 逐步对着当前活页面执行：每个动作先在当前观察里解析目标，失败了错误回给模型重新瞄准（`LOCATOR_NOT_FOUND` → re-aim），最后过断言，通过才录制。录制的正确性是**被证明的**。这不是"换一种 DSL 生成代码"，是**批量发射 vs 交互校准**的区别。

| | 生成 Playwright 脚本 | e2e |
|---|---|---|
| 首跑产物 | 完整脚本（**代码**） | 一句话 goal + 断言 + 录制（**数据**） |
| UI 改版后 | 测试红或 flake，人读代码分辨"产品 bug 还是脚本过期" | `REPLAY_STALE` 指名步骤；`--no-cache` 重录，断言重新把关 |
| 长期维护对象 | 整份脚本代码 | 一句话 + 一行断言（录制是数据，自动换） |
| flake 来源 | 生成的等待、选择器竞态，逐个排查 | 没人写等待；轮询与匹配语义由引擎统一提供 |
| 需求权威 | 每次重新生成都是对需求的一次重新解释，漂移悄悄累积 | 重录只重新推导"怎么做"；"测什么、对错"永远钉在人写的 goal 和断言上 |

**"要让 LLM 重新学一门语言"的说法反了。** 两层来看：作者面 SDK 只有五六个 API（`test`、`agent.act`、`expect`、`session`、`setup`），比 Playwright 的 API 面小一个量级，skill 只是随包分发的引导材料；执行面 agent 用的根本不是"语言"，而是**受校验的工具调用**（闭 schema、逐步授权），目标定位靠引擎的语义树（角色、可访问名、状态——拿 Chrome 无障碍树和 axe-core 交叉验证过的那套）。选择器定位 DOM，语义定位含义。复杂度没有转嫁给模型权重，而是放在框架运行时里：语义匹配、轮询、回放、密钥遮蔽——这些是 Playwright 权重知识替代不了的工程。

**诚实的边界。** 什么时候 codegen 方案够用甚至更好：已有 Playwright 底子和 CI harness、团队熟；数据驱动/参数化测试、纯 API 流程（代码本来就更合适，e2e 里这类也仍是代码写）；改版少、维护期短的一次性项目。e2e 拉开差距的场景：长期维护、UI 改版频繁、flake 敏感、需要移动端同一套写法（`device` fixture 覆盖原生 app，Playwright 只覆盖 web）、需要探索和密钥纪律作为一等公民。

## 8. e2e 必须独立建测试项目？Playwright 就该放被测项目里？

都不是——**放哪里是工程组织决策，不是工具属性**。两者都既能放被测项目里，也能独立成仓库。e2e 官方 Web 示例（`examples/with-vite` 等）就是测试和被测应用同一个目录，原生项目则在旁边放一个 `e2e/` 文件夹；Playwright 同样有大量独立测试仓库的用法（测外部系统、多环境回归的团队常这么干）。e2e 对位置的唯一要求：那个目录里有 `e2e.config.ts`、`tests/*.e2e.ts` 和 package.json 依赖。

| | 放被测项目里 | 独立测试项目 |
|---|---|---|
| 改动原子性 | UI 改动 + 测试更新 + 重录**同一个 PR**，CI 天然联动 | 跨仓库两次提交，自己保证顺序 |
| 边界 | 白盒方便（能 import 源码、读 fixture） | 黑盒被物理强制，测试只能看见服务本身 |
| 工具链 | 被测仓库背上测试工具全套依赖 | 各自干净（Python 仓库不用装 Node） |
| 节奏 | 测试随应用一起发布 | 独立演进，可测多套环境 |

本文的考试系统案例选了独立仓库，三条理由：工具链隔离（被测是 Python + FastAPI，e2e 是 Node/TypeScript）；黑盒边界物理化（测试只依赖 `http://127.0.0.1:8000`，不碰源码）；被测仓库内已有一套 pytest-Playwright（临时库、确定性）承担"随代码走"的那层，e2e 补"对部署服务黑盒 + agent 驱动"这一层。代价是 UI 改版后要跨两个仓库提交（先提交应用改动，再去测试仓库重录并提交）——单人开发可忽略，多人团队加 CI 拦合并时这个成本会放大，那时"放在一起"反而更合理。哪天想搬回去也只是挪目录、装依赖的事，框架层面没有任何障碍。

## 心智模型一页纸

- **工作流**：规格（人）→ 薄测试（一句话 goal + 一行断言）→ 首跑录制（唯一花钱处）→ 回归零成本回放 → 改版重录同提交
- **知识分工**：覆盖面和业务规则来自人；页面结构来自 MCP 实时观察；explore 命令只负责找未知
- **规则注入三级**：agent 通用常识 < 规则写进 goal 文本 < 规则变成断言
- **定位**：取代"手"不取代"脑"；操作用自然语言，对错用断言；自然语言只解释一次
- **vs codegen Playwright**：开环生成"被相信的代码" vs 闭环执行"被证明的录制"；维护对象是整份脚本 vs 一句话加断言
- **项目位置**：正交决策，按工具链、边界、改动原子性权衡，两个工具哪个方向都能放
